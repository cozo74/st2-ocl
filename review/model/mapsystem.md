# JevPilot 地图系统静态模型

本文档只整理 JevPilot 地图系统的静态表示：地图由哪些数据构成、采用什么坐标系，以及道路、对象和路线之间如何关联。

暂不讨论对象的动态更新、车辆控制、预测、候选轨迹和三维渲染。文档按照模型之间的关系组织；必要时使用结构图、空间示意图或对照表帮助理解。

## 1. 地图系统总览

JevPilot 的地图不是一张图片，而是保存在 `world` 中的结构化世界模型。它主要由以下部分组成：

```text
world
├─ 地图元数据与范围
├─ 道路拓扑
├─ 连续道路几何
├─ 地图对象
└─ 起点、目的地与规划路线
```

### 1.1 地图容器 `world`

`world` 是地图的总容器，典型结构为：

```js
{
  seed,
  type,
  theme,
  bounds,

  nodes,
  byId,
  edges,
  objects,

  startNode,
  nextNode,
  destination,
  route
}
```

- `seed`：程序化生成地图的随机种子；
- `type`：`town`、`city` 或 `highway`；
- `theme`：地图名称、默认限速等环境参数；
- `bounds`：地图在世界坐标中的总体范围。

地图的逻辑几何使用二维 `x-z` 平面，单位为米：`+x` 向东，`+z` 向南；`y` 不属于当前讨论的地图平面表示。

### 1.2 道路拓扑

道路拓扑使用图结构表示：

```text
node A ●──────── edge ────────● node B
```

- `nodes`：路口或道路连接点，保存 ID、世界位置、相邻节点和交通控制类型；
- `edges`：节点之间的道路，保存起止节点、宽度、限速、名称和道路类型；
- `byId`：从节点 ID 到节点对象的快速索引。

拓扑图回答“哪些道路相互连通”，但不直接描述完整的沥青形状。

### 1.3 连续道路几何

道路的空间形状使用连续几何表示：

- 城镇和城市：根据道路边的起止位置与宽度构造道路面；
- 高速主路：使用 `roadSamples` 保存中心线采样点 `(x,z,s)`；
- 匝道、合流段和出口：使用 `connectorRoads` 保存采样曲线和道路宽度；
- 可行驶区域：由上述数据展开成二维道路多边形集合。

其中 `s` 表示沿采样曲线从起点开始累计的距离。

因此，地图同时具有两种道路表示：

```text
nodes + edges         表示连接关系
曲线 + 道路多边形      表示实际空间形状
```

### 1.4 地图对象

静态地图对象统一保存在 `world.objects` 中，每个对象至少具有：

```js
{
  id,
  type,
  x,
  z
}
```

其他字段由 `type` 决定。例如：

| 类别 | 类型示例 | 主要附加表示 |
| --- | --- | --- |
| 建筑与地块 | `building`、`parcel` | 尺寸、高度、旋转或用途 |
| 交通设施 | `stop_sign`、`traffic_light` | 所属路口和面向方向 |
| 环境对象 | `tree`、`bench`、`streetlight` | 高度、种类或旋转 |
| 高速环境 | 标牌、山体、高架桥 | 文本、方向和三维尺寸 |

交通设施通过 `nodeId` 与道路拓扑中的路口节点关联，而不是孤立地放置在地图中。

### 1.5 起点、目的地与路线

`startNode`、`nextNode` 和 `destination` 引用道路拓扑中的节点。`world.route` 则表示在完整地图上选出的一条具体路径：

```js
{
  ids,        // 经过的节点
  points,     // 连续路径采样点 (x,z,s)
  crossings,  // 经过的路口和停止线
  sections,   // 高速路线的分段信息
  length
}
```

需要区分：

```text
地图：描述所有可用道路和静态对象
路线：描述在地图上选中的一条通行路径
```

路线依赖地图，但路线本身不是完整地图。

### 1.6 组成关系小结

| 地图组成 | 表示方式 | 作用 |
| --- | --- | --- |
| 地图范围 | `bounds` | 描述世界坐标范围 |
| 道路拓扑 | `nodes + edges` | 描述道路连通关系 |
| 道路几何 | 采样曲线和多边形 | 描述道路实际形状 |
| 地图对象 | 带 `type` 的对象数组 | 描述建筑、设施和环境 |
| 规划路线 | 节点序列和采样曲线 | 描述选中的通行路径 |

地图系统的核心表示方式是：用图结构描述连通性，用曲线和多边形描述空间形状，用带类型的对象描述静态地图内容。

### 1.7 `world` 与完整地图系统的关系

`world` 是地图系统的主数据容器，但不是所有地图表示都作为字段直接存放在其中。

```text
world 中的基础地图数据
├─ nodes、edges                 道路拓扑
├─ objects                      静态地图对象
├─ bounds、type、theme          地图范围与元数据
├─ roadSamples、connectorRoads  高速连续几何数据
└─ route                        当前规划路线
             │
             ▼ 计算
world 外的派生地图表示
└─ 道路多边形、局部道路边界等
```

可以分为三类：

| 内容 | 是否在 `world` 中 | 说明 |
| --- | --- | --- |
| 地图基础数据 | 是 | 例如节点、道路边、静态对象和地图范围 |
| 派生几何 | 否，按需计算 | 例如 `roadGeometry(world)` 生成的可行驶道路多边形 |
| 非地图状态 | 否 | ego、NPC、行人等保存在 `Simulation` 中 |

因此，更准确的说法是：

> `world` 包含地图系统的主要源数据；道路多边形等派生结果由这些数据计算得到，动态实体则属于其他模型。

### 1.8 地图元数据与范围

这里所说的地图元数据，主要是 `world` 中描述地图来源和整体环境的字段：

```js
{
  seed,
  type,
  theme,
  bounds
}
```

#### 地图元数据

| 字段 | 含义 |
| --- | --- |
| `seed` | 程序化生成地图使用的随机种子；相同 `seed + type` 用于复现相同地图 |
| `type` | 地图环境类型：`town`、`city` 或 `highway` |
| `theme` | 当前地图类型的名称、默认限速和生成参数 |

`theme` 的典型结构为：

```js
{
  name,
  subtitle,
  size,
  traffic,
  buildings,
  limit,
  laneOffset // 仅高速主题使用
}
```

| `theme` 字段 | 含义 |
| --- | --- |
| `name/subtitle` | 地图名称和说明文字 |
| `size` | 城镇/城市路网的生成规模；不是米制宽度 |
| `traffic` | 交通对象的目标生成数量参数 |
| `buildings` | 建筑地块生成密度参数 |
| `limit` | 地图默认限速，单位为 `m/s` |
| `laneOffset` | 高速路线相对中心线的默认横向偏移，单位为米 |

`theme` 是生成和环境配置，不是具体道路几何。例如真实道路宽度仍保存在各个 `edge` 中。

#### 地图范围 `bounds`

地图范围使用 `x-z` 平面中的轴对齐矩形表示：

```js
bounds: {
  minX,
  maxX,
  minZ,
  maxZ
}
```

示意如下：

```text
                     minZ
                       ▲
          (minX,minZ) ┌──────────────┐ (maxX,minZ)
                      │              │
              minX ◄──│    地图范围   │──► maxX
                      │              │
          (minX,maxZ) └──────────────┘ (maxX,maxZ)
                       ▼
                     maxZ
```

由于项目规定 `+z` 向南，因此图中的北侧对应较小的 `z`，南侧对应较大的 `z`。

范围可以写成集合：

\[
minX \le x \le maxX,
\qquad
minZ \le z \le maxZ
\]

`bounds` 只表示地图整体允许覆盖的矩形区域，不表示道路边界：矩形内部既可能有道路，也可能有建筑、草地或其他非行驶区域。

城镇和城市先使用 `xs`、`zs` 保存道路网格中心线的坐标，再在最外侧道路之外增加边距形成 `bounds`：

```js
{
  minX: xs[0] - 28,
  maxX: xs.at(-1) + 28,
  minZ: zs[0] - 28,
  maxZ: zs.at(-1) + 28
}
```

这里的 `xs/zs` 属于路网布局数据，不是元数据。高速地图则直接给出适合整段高速、匝道和两端城镇的固定矩形范围。

## 2. 城镇与城市路网生成

### 2.1 为什么城镇路网横平竖直

这是 `town/city` 地图生成算法明确规定的结果。算法先分别生成一组 `x` 坐标和一组 `z` 坐标：

```js
xs = [x0, x1, x2, ...]
zs = [z0, z1, z2, ...]
```

然后用二者的笛卡尔组合生成路口节点：

```js
node(i, j) = {
  x: xs[i],
  z: zs[j]
}
```

因此所有节点都落在正交网格上：

```text
z0   ●──────●────────●─────●
     │      │        │     │
z1   ●──────●────────●─────●
     │      │        │     │
z2   ●──────●────────●─────●
     x0     x1       x2    x3
```

连接节点时只采用两种方式：

1. 连接同一行的相邻节点：`j` 相同、`i` 相差 1，因此 `z` 不变，是水平道路；
2. 连接同一列的相邻节点：`i` 相同、`j` 相差 1，因此 `x` 不变，是竖直道路。

算法中的随机性只影响：

- 相邻 `x` 坐标或 `z` 坐标之间的距离；
- 某些竖直连接是否被省略；
- 建筑、公园和目的地等布局。

它不会旋转道路，也不会连接斜对角节点，所以不会生成斜向道路。

需要区分道路和车辆路线：道路主体是横平竖直的，但车辆通过路口转弯时，`route.points` 会在两条正交道路之间生成平滑转弯曲线。

`highway` 地图不受这一正交网格限制。它的主路由平滑采样曲线表示，匝道、合流段和出口也可以是斜向或弯曲的。

### 2.2 道路间距和纵向连接的随机逻辑

`town/city` 使用由 `seed` 初始化的确定性随机数生成器 `r`。同一个 `seed + type` 会产生相同的间距和连接结果。

#### 道路间距

`xs` 和 `zs` 都从 `0` 开始，后一个坐标由前一个坐标加上“基础间距 + 随机增量”得到：

```js
xs.push(xs.at(-1) + base + Math.floor(r() * 55));
zs.push(zs.at(-1) + base + Math.floor(r() * 55));
```

其中：

| 地图类型 | `base` | 实际相邻间距 |
| --- | ---: | ---: |
| `town` | `110 m` | `110–164 m` |
| `city` | `125 m` | `125–179 m` |

`Math.floor(r() * 55)` 产生 `0–54` 的整数。`x` 和 `z` 分别调用随机数，所以横向街区宽度和纵向街区长度可以不同。

生成完坐标后，系统把所有坐标整体平移，使路网中心接近世界原点。该平移不会改变道路间距。

#### 道路连接

对于网格节点 `(i,j)`，连接规则是：

```js
// 水平边：全部保留
if (i < n - 1)
  link(node(i, j), node(i + 1, j));

// 纵向边：强制骨架或随机保留
if (
  j < n - 1 &&
  (i === 2 || (i === 1 && j === 1) || r() > 0.16)
)
  link(node(i, j), node(i, j + 1));
```

规则可以概括为：

| 连接 | 规则 |
| --- | --- |
| 水平连接 | 全部生成 |
| 第 `i=2` 列的纵向连接 | 全部生成，形成贯穿上下的纵向骨架 |
| `(i=1,j=1)` 的纵向连接 | 强制生成，保证预设起始路段存在 |
| 其他纵向连接 | `84%` 概率生成，`16%` 概率省略 |

示意图中，虚线表示可能被随机省略的纵向道路：

```text
●────●────●────●────●
┆    ┆    │    ┆    ┆
●────●────●────●────●
┆    │    │    ┆    ┆
●────●────●────●────●
┆    ┆    │    ┆    ┆
●────●────●────●────●
┆    ┆    │    ┆    ┆
●────●────●────●────●
          ↑
      i=2 强制纵向骨架
```

因为所有水平道路都存在，并且 `i=2` 列贯穿所有行，所以每一行都能接入纵向骨架，整个路网始终连通。随机省略其他纵向边只会改变可选路线和道路稀疏程度，不会把地图分裂成互不连通的区域。

### 2.3 正交点阵的节点数和连接规则

上述理解基本正确，但当前代码使用同一个 `n=theme.size` 控制两个方向，因此生成的是 `n×n` 方形点阵，而不是分别配置的 `m×n` 点阵。生成完成后，主题保存在 `world.theme` 中，所以也可以写成 `n=world.theme.size`；`world` 本身没有直接的 `size` 字段。当前 `town/city` 的 `n` 都是 `5`。

这里的 `size` 只直接控制 `town/city` 的正交点阵规模。虽然高速主题也定义了 `theme.size`，但 `highway` 使用单独的显式节点和曲线生成逻辑，不按 `size×size` 构造点阵。

节点坐标满足：

\[
node(i,j)=(xs[i],zs[j])
\]

因此：

- 同一行的所有节点具有相同的 `z=zs[j]`；
- 同一列的所有节点具有相同的 `x=xs[i]`；
- 所有行相互平行；
- 所有列相互平行；
- 行与列保持垂直。

间距随机性作用于整对相邻行或整对相邻列：

```text
列间距：xs[i+1] - xs[i]
行间距：zs[j+1] - zs[j]
```

例如，`xs[2]-xs[1]` 一旦生成，这个距离就适用于第 2 列和第 3 列之间的所有行，不会每一行重新随机。

边的规则是：

- 每行的所有相邻节点都有水平 `edge`；
- 按从 `0` 开始的索引，`i=2` 是第 3 列，该列所有上下相邻节点都有纵向 `edge`；
- `(i=1,j=1)` 到其下一行的纵向 `edge` 也强制存在；
- 其他上下相邻节点以 `84%` 概率连接。

## 3. 高速公路地图生成

### 3.1 高速公路地图的整体生成算法

高速地图采用“固定模板 + 少量随机扰动”，而不是随机生成道路拓扑。因此不同 `seed` 下仍会看到相同的整体路线：

```text
Millbrook
   │
   ├─ 本地街道
   │
   └─ 入口匝道 → 加速/合流 → Interstate 08 → 出口匝道 → Cedar Town
```

生成过程可以分为六步。

#### 1. 生成高速主路控制点

系统固定生成 9 个主路节点 `h0` 到 `h8`：

```js
x = sin(i * 0.65 + phase) * 48;
z = 680 - i * 170;
```

其中：

```js
phase = random() * 2;
```

- `z` 每次固定减少 `170 m`，决定高速整体从南向北延伸；
- `x` 按固定振幅和频率左右摆动，形成缓弯；
- `seed` 只通过一个随机 `phase` 改变弯曲相位，不改变节点数量和排列顺序。

#### 2. 把控制点平滑成主路中心线

9 个节点只定义大致走向。`smoothRoad()` 使用相邻四个控制点进行三次插值，把折线变成平滑曲线，再按约 `2 m` 间距重采样：

```text
h0 ●────● h1────● h2          原始控制点
        ↓ 平滑和重采样
   ╭──────────────╮            roadSamples
```

结果保存在：

```js
roadSamples: [{ x, z, s }, ...]
```

#### 3. 建立固定的高速拓扑

系统依次连接：

```text
h0—h1—h2—h3—h4—h5—h6—h7—h8
```

每段都使用固定属性：

```js
{
  width: 25,
  speedLimit: 28,
  kind: "interstate",
  name: "Interstate 08"
}
```

因此主路拓扑不会随 `seed` 改变。

#### 4. 添加两端城镇和连接道路

Millbrook 和 Cedar Town 的节点布局、道路连接和相对位置都由源码模板明确给出。

关键道路包括：

```text
本地街道
→ ramp_turn
→ onramp
→ merge
→ interstate
→ exit
→ offramp
→ 目的地城镇道路
```

两个城镇会根据高速曲线的横向位置整体平移，但内部拓扑基本不变。

#### 5. 生成匝道、合流和出口曲线

- 入口和出口匝道使用三次 Bézier 曲线；
- 合流段从主路侧向偏移 `15 m` 平滑收敛到 `9 m`；
- 出口段从 `9 m` 平滑外移到 `17 m`；
- 曲线按约 `1.5 m` 间距采样，并保存到 `edge.path` 和 `connectorRoads`。

合流和出口位置也是固定选择的：

```text
h2 → h3 附近：合流
h6 之后：出口
```

#### 6. 添加静态环境对象并构造默认路线

建筑、路灯、停车标志、道路标牌和高架桥的位置大多使用固定模板。树木、山体、建筑颜色等外观细节使用 `seed` 随机生成。

默认路线节点顺序固定为：

```text
local-start
→ mill-market
→ mill-interchange
→ onramp
→ merge-lane
→ h3 → h4 → h5 → h6
→ exit-cedar
→ cedar-town
→ cedar-stop
```

#### 固定部分与随机部分

| 基本固定 | 随 `seed` 变化 |
| --- | --- |
| 主路节点数量和连接顺序 | 主路正弦曲线的相位 |
| 主路宽度、限速和名称 | 主路在 `x` 方向的具体弯曲位置 |
| 两端城镇的内部拓扑 | 两端城镇随主路产生的整体横向位置 |
| 入口、合流、出口和目的地顺序 | 树木和山体的位置、大小与种类 |
| 合流位于 `h2–h3`，出口位于 `h6` 后 | 部分建筑颜色 |
| 默认规划路线 | 其他环境装饰细节 |
| 地图总体 `bounds` |  |

所以实践中感觉地图固定是正确的：`seed` 不会生成另一套高速拓扑，只会在固定场景模板上改变曲线相位和环境细节。

### 3.2 主路正弦曲线的相位

高速主路节点的横向坐标按下式生成：

\[
x_i=48\sin(0.65i+phase)
\]

```js
phase = random() * 2;
```

`phase` 是正弦函数内部的起始角度偏移，单位为弧度。它不是道路航向，也不是直接给所有节点增加一个固定的 `x` 位移。

可以把它理解为：在同一条正弦波上，从不同位置开始取样。

```text
phase 较小：     ·╭──╮    ╭──╮
              ·╯    ╰──╯

phase 较大：   ╭──╮    ╭──╮·
                ╰──╯    ╰·
              正弦摆动模式整体错开
```

例如第一个节点 `i=0`：

\[
x_0=48\sin(phase)
\]

- `phase=0` 时，`x₀=0`；
- `phase=π/2` 时，`x₀=48`。

相位变化会同时改变所有主路节点的 `x` 坐标，但以下内容保持不变：

- 振幅仍为 `48 m`；
- 相邻节点的正弦角度增量仍为 `0.65 rad`；
- 节点的 `z` 间距仍为 `170 m`；
- 节点数量和连接拓扑不变。

当前代码使用 `random()*2`，所以 `phase` 的范围是 `[0,2)` 弧度，并没有覆盖完整的 `[0,2π)` 正弦周期。

因此，`phase` 改变的确实是高速公路主路在俯视平面上的弯曲形状，更准确地说是改变各个主路控制点的横向位置。平滑后的 `roadSamples`、由其展开的道路面，以及沿主路生成的车辆路线都会随之变化；道路宽度、节点顺序和连接拓扑则保持不变。

### 3.3 两端城镇与匝道是否固定

需要区分“拓扑和生成模板固定”与“最终绝对坐标完全固定”。

| 部分 | 固定内容 | 可能变化的内容 |
| --- | --- | --- |
| Millbrook | 节点布局、街道连接、入口方向 | 整体 `x` 位置随主路横向位置移动 |
| Cedar Town | 目的地道路、横向支路和建筑相对布局 | 整体 `x` 位置随主路横向位置移动 |
| 入口匝道 | 生成方式、宽度、限速、连接顺序 | Bézier 曲线的端点和切线方向 |
| 合流段 | 固定连接 `h2–h3` 区域，横向偏移由 `15 m` 收敛到 `9 m` | 具体世界坐标随主路曲线变化 |
| 出口段 | 固定从 `h6` 附近开始，并在其后约 `80 m` 分离 | 具体世界坐标和切线方向 |
| 出口匝道 | 固定连接高速出口与 Cedar Town | 曲线根据出口点和城镇入口自适应 |

两端城镇的横向基准位置按主路计算：

```js
startX = max(h0.x, h1.x, h2.x) + 145;
townX  = max(h6.x, h7.x, h8.x) + 155;
```

所以城镇内部形状基本固定，但会随着高速主路的正弦相位整体左右移动。

匝道连接位置在拓扑意义上固定：

```text
h2—h3 区域：入口合流
h6 之后约 80 m：出口分离
```

但匝道曲线端点取自当前的 `roadSamples`，控制点还会使用该位置的主路航向。因此 `phase` 改变后，匝道仍连接到相同的语义位置，但具体坐标和弯曲形状会稍有变化。

可以概括为：

> 城镇和匝道的布局规则、道路顺序与连接位置固定；绝对位置和曲线细节会对当前高速主路形状进行适配。

### 3.4 匝道为什么看起来比高速单车道宽

观察正确。项目中高速单车道和匝道使用了不同的宽度参数。

高速路线分段中的车道半宽为：

```js
laneHalfWidth = 2.25; // interstate
```

所以高速单车道的名义宽度为：

\[
2\times2.25=4.5\text{ m}
\]

非高速路线分段统一使用：

```js
laneHalfWidth = 3;
```

对应名义车道宽度：

\[
2\times3=6\text{ m}
\]

各连接道路的实际道路面宽度为：

| 路段 | `edge.width` |
| --- | ---: |
| 高速主路整体 | `25 m` |
| 入口转弯段 `ramp_turn` | `8 m` |
| 入口匝道 `onramp` | `6 m` |
| 合流段 `merge` | `6 m` |
| 出口段 `exit` | `6 m` |
| 出口匝道 `offramp` | `6 m` |
| 城镇本地道路 | `12 m` |

需要注意，高速主路的 `25 m` 是包括两个方向和中央隔离带在内的总体道路宽度，不能直接与单条匝道比较。高速道路几何实际分成左右两个方向的道路带，中间保留约 `2.1 m` 的不可行驶隔离区。

因此视觉上的比较是：

```text
高速单车道：        约 4.5 m
普通单向匝道：      约 6.0 m
入口转弯道路面：    约 8.0 m
```

普通匝道在当前模型中确实比高速单车道宽约 `1.5 m`。入口转弯段的 `8 m` 是道路面宽度，而其路线仍按非高速段的 `6 m` 名义车道宽度表示，因此两侧还各有约 `1 m` 的额外道路余量。

### 3.5 匝道宽度在哪里设置

匝道道路面宽度在 `src/highway.js` 的 `generateHighway()` 中设置。内部函数 `link()` 的第 4 个参数是 `width`：

```js
link(a, b, surface, width, speed, kind, name, ...);
```

各匝道在调用 `link()` 时直接传入固定宽度：

```js
link(rampJunction, ramp, ..., 8,  8, "ramp_turn", ...);
link(ramp, merge,        ..., 6, 26, "onramp",   ...);
link(merge, h3,          ..., 6, 26, "merge",    ...);
link(h6, exit,           ..., 6, 22, "exit",     ...);
link(exit, town,         ..., 6, 16, "offramp",  ...);
```

`link()` 会把该值保存到两个位置：

```js
edges.push({ ..., width, ... });
connectorRoads.push({ ..., width, ... });
```

- `edge.width`：道路拓扑和属性中的宽度；
- `connectorRoads.width`：生成实际道路带几何时使用的宽度。

路线的逻辑车道半宽在 `makeHighwayRoute()` 中单独设置：

```js
laneHalfWidth = edge.kind === "interstate" ? 2.25 : 3;
```

所以修改匝道道路面宽度时应检查 `link()` 调用中的 `width`；修改路线使用的逻辑车道宽度时则应检查 `laneHalfWidth`。

### 3.6 高速连接路段的类型

`ramp_turn`、`onramp`、`merge`、`exit` 和 `offramp` 是高速复合路线中不同道路段的 `kind`。它们按以下顺序连接：

```text
Millbrook 本地道路
        │
        ▼
 ramp_turn  入口转弯段
        │
        ▼
  onramp    入口匝道
        │
        ▼
   merge    合流段
        │
        ▼
 interstate 高速主路
        │
        ▼
    exit    出口分离段
        │
        ▼
  offramp   出口匝道
        │
        ▼
Cedar Town 本地道路
```

| `kind` | 起点与终点 | 静态几何含义 | 宽度 | 限速 |
| --- | --- | --- | ---: | ---: |
| `ramp_turn` | `mill-interchange → onramp` | 从 Millbrook 路口转入高速入口的短连接道路 | `8 m` | `8 m/s` |
| `onramp` | `onramp → merge-lane` | 使用三次 Bézier 曲线连接本地道路和高速合流区 | `6 m` | `26 m/s` |
| `merge` | `merge-lane → h3` | 沿高速方向逐渐从外侧偏移位置收敛到主路车道 | `6 m` | `26 m/s` |
| `exit` | `h6 → exit-cedar` | 从主路车道逐渐向外侧分离的出口段 | `6 m` | `22 m/s` |
| `offramp` | `exit-cedar → cedar-town` | 使用三次 Bézier 曲线连接高速出口与 Cedar Town | `6 m` | `16 m/s` |

#### `ramp_turn`

定义在 `src/highway.js` 的 `link(rampJunction, ramp, ...)` 调用中。它使用两个端点形成直线连接，`kind="ramp_turn"`，宽度为 `8 m`。

#### `onramp`

定义在 `link(ramp, merge, ...)` 调用中。其道路中心线由 `cubic(...)` 生成，从入口点弯向高速合流点，`kind="onramp"`，宽度为 `6 m`。

#### `merge`

定义在 `link(merge, byId.h3, ...)` 调用中。它位于高速节点 `h2–h3` 附近，中心线相对高速主中心线的横向偏移从 `15 m` 平滑减小到 `9 m`，表示汇入主路车道。

#### `exit`

定义在 `link(byId.h6, exit, ...)` 调用中。它从 `h6` 所在位置开始，在随后约 `80 m` 内将横向偏移从 `9 m` 平滑增加到 `17 m`，表示从主路向出口外移。

#### `offramp`

定义在 `link(exit, town, ...)` 调用中。它用 `cubic(...)` 生成从高速出口到 Cedar Town 入口的弯曲连接，`kind="offramp"`，宽度为 `6 m`。

这些类型值由 `link()` 同时写入 `edge.kind` 和 `connectorRoads.kind`，用于区分各段道路的语义及几何。

### 3.7 高速地图的辅助静态字段

#### `shoulderOpenings`

`shoulderOpenings` 是高速主路路肩开口的里程区间数组：

```js
[
  [startS1, endS1],
  [startS2, endS2]
]
```

当前生成的两个区间分别对应汇入区和驶出区。这里的数值不是 `(x,z)` 坐标，而是高速主路中心采样线 `roadSamples` 上的累计里程 `s`：

```text
高速中心线 ───────────────→ s
             [开口 1]   [开口 2]
              汇入区      驶出区
```

它也不是道路多边形。它只标记“在哪一段里程范围内，主路与匝道衔接处不应被连续路肩分隔”。从当前源码引用来看，该字段没有参与 `roadGeometry()` 的道路多边形、路线规划或碰撞逻辑，因此应把它理解为高速地图的辅助空间注记，而不是核心可行驶区域定义。

#### `destinationStopLine`

`destinationStopLine` 是终点附近的一个静态标记：

```js
{
  x,
  z,
  heading
}
```

它由默认路线最后一个点再偏移 1.4 m 得到，`heading` 固定为 `0`。它与 `route.crossings[].stopS` 不同：

| 字段 | 表示方式 | 含义 |
|---|---|---|
| `crossing.stopS` | 路线累计里程 | 某个途中路口的停车位置 |
| `destinationStopLine` | 世界坐标和航向 | 默认路线终点附近的独立终点标记 |

从当前源码引用来看，`destinationStopLine` 也没有进入路线生成、车辆运动或停车判断逻辑。因此在只讨论静态逻辑地图时，它同样属于附加地图标记，不应误认为决定任务是否完成的核心路线字段。

## 4. 道路几何与可行驶区域

### 4.1 Node 和道路几何形状的表示

路网图建立后，项目仍然区分“拓扑表示”和“几何表示”：

```text
拓扑层                         几何层
node + edge       ───────►    点、采样曲线、道路多边形
描述如何连接                   描述道路实际占据哪里
```

#### Node 的表示

一个 `node` 本身只是世界坐标中的点，不是一个有面积的路口：

```js
{
  id,
  x,
  z,
  neighbors,
  control,
  offset
}
```

其中 `(x,z)` 是节点中心位置，`neighbors` 表示拓扑连接。节点的路口面积由后续道路几何生成，而不是直接存放在 `node` 中。

#### 城镇和城市的直线路面

普通 `edge` 保存两个端点节点的 ID 和道路宽度：

```js
{
  a,
  b,
  width
}
```

系统取得节点 `a`、`b` 的坐标，计算从 `a` 指向 `b` 的方向，再把中心线向左右各偏移 `width/2`，得到四个角点：

```text
左边界  Lₐ ●────────────────● Lᵦ
            │                │
中心线   A ●────────────────● B
            │                │
右边界  Rₐ ●────────────────● Rᵦ
```

对应道路多边形为：

```js
[L_a, R_a, R_b, L_b]
```

当前城镇道路宽度是 `12 m`，所以中心线左右各展开 `6 m`。

为了填补多条道路矩形在节点处形成的空隙，每个节点还会生成一个以 `(x,z)` 为中心、半边长约 `6.05 m` 的方形路口面：

```text
             道路
              │
        ┌─────┼─────┐
道路 ───┼──── node ──┼─── 道路
        └─────┼─────┘
              │
             道路
```

#### 高速主路的曲线路面

高速主路不能只用相邻节点之间的单个矩形表示。系统先把 `h0–h8` 平滑为采样中心线：

```js
roadSamples: [
  { x, z, s },
  { x, z, s },
  // ...
]
```

对每对相邻采样点，系统沿局部切线的垂直方向取左右偏移点，形成一个四边形道路片。所有道路片首尾相接，近似出连续弯曲道路：

```text
采样中心线：     ●──●──●──●
                  ╲       ╲
道路带：        ╱────────────╲
              ╱                ╲
              ╲                ╱
                ╲────────────╱
```

高速道路被分成两个方向的道路带：

```text
左侧道路带：中心线偏移 [-12.5, -1.05] m
中央隔离区：          [-1.05, +1.05] m
右侧道路带：中心线偏移 [+1.05, +12.5] m
```

中央约 `2.1 m` 不属于可行驶道路面。

#### 匝道和连接道路

匝道几何保存在：

```js
connectorRoads: [{
  points: [{ x, z, s }, ...],
  width,
  kind
}]
```

系统对采样曲线的每一小段分别向左右偏移 `width/2`，生成连续四边形道路片。直线、Bézier 匝道、合流和出口最终都转换成同一种多边形道路面表示。

#### 最终道路多边形

每个道路片在内部表示为：

```js
{
  points: [{ x, z }, ...],
  minX,
  maxX,
  minZ,
  maxZ
}
```

- `points`：多边形顶点；
- `minX/maxX/minZ/maxZ`：该多边形的轴对齐包围范围，用于快速空间筛选。

`roadGeometry(world)` 返回所有道路片组成的多边形数组，并对结果进行缓存。它们是从 `world` 的节点、边和采样曲线派生的，不直接作为固定字段存回 `world`。

因此完整关系为：

```text
node：空间中的连接点
edge：节点之间的拓扑连接和道路属性
采样曲线：弯曲道路的中心轨迹
道路多边形：道路最终占据的二维空间
```

### 4.2 城镇道路的几何表示

`town` 和 `city` 使用相同的道路几何生成方法。由于路网只包含水平和竖直道路，每条道路边都可以表示成一个矩形沥青面。

#### 1. 从拓扑边取得中心线

一条道路边只保存端点 ID 和道路属性：

```js
edge = {
  a,           // 起点 node ID
  b,           // 终点 node ID
  width: 12,
  length,
  speedLimit,
  name
};
```

通过 `world.byId` 取得端点：

```js
const a = world.byId[edge.a];
const b = world.byId[edge.b];
```

线段 `A→B` 就是这条道路的几何中心线：

```text
A ●────────────────────────● B
```

#### 2. 计算道路方向

道路方向由两个端点计算：

\[
h=\operatorname{atan2}(b_x-a_x,\;a_z-b_z)
\]

项目代码写作：

```js
h = heading(a, b);
```

由于城镇节点位于正交点阵中，`h` 只会对应东、西、南、北四种方向。

#### 3. 从中心线向两侧展开

城镇道路宽度为：

\[
w=12\text{ m}
\]

所以中心线左右各展开：

\[
\frac{w}{2}=6\text{ m}
\]

以道路方向 `h` 为基准：

```js
leftA  = move(a, h - Math.PI / 2, width / 2);
rightA = move(a, h + Math.PI / 2, width / 2);
leftB  = move(b, h - Math.PI / 2, width / 2);
rightB = move(b, h + Math.PI / 2, width / 2);
```

形成道路矩形：

```text
leftA  ●────────────────────────● leftB
       │                        │
     A ●────────────────────────● B    中心线
       │                        │
rightA ●────────────────────────● rightB
               12 m 宽
```

道路多边形的顶点为：

```js
[leftA, rightA, rightB, leftB]
```

#### 4. 水平道路示例

假设：

```text
A = (0, 0)
B = (100, 0)
width = 12
```

这是一条向东的道路。展开后四个角为：

```text
(0,-6) ┌──────────────────┐ (100,-6)
       │                  │
       │                  │
(0,+6) └──────────────────┘ (100,+6)
```

因此道路占据：

\[
0\le x\le100,
\qquad
-6\le z\le6
\]

#### 5. 节点处的路口面

道路矩形只描述道路边。为了把同一节点周围的多条道路连接成完整路口，每个节点还会生成一个方形道路面：

```js
[
  { x: node.x - 6.05, z: node.z - 6.05 },
  { x: node.x + 6.05, z: node.z - 6.05 },
  { x: node.x + 6.05, z: node.z + 6.05 },
  { x: node.x - 6.05, z: node.z + 6.05 }
]
```

也就是以节点为中心、边长约 `12.1 m` 的正方形：

```text
              北向道路
                 │
           ┌─────┼─────┐
西向道路 ──┤     ●     ├── 东向道路
           └─────┼─────┘
                 │
              南向道路
```

半边长使用 `6.05 m`，略大于道路半宽 `6 m`，使路口面与相邻道路面有微小重叠，避免几何接缝。

#### 6. 整张道路由多边形集合表示

系统不会把所有道路预先合并成一个巨大的复杂多边形，而是保存为多个简单道路片：

```text
每条 edge  → 一个矩形道路面
每个 node  → 一个方形路口面
所有道路面 → surfaces 数组
```

每个道路片都表示为：

```js
{
  points,
  minX,
  maxX,
  minZ,
  maxZ
}
```

其中包围范围用于快速排除距离很远、不可能相交的道路片。

#### 7. 道路面和路线的区别

城镇地图中存在三种容易混淆的表示：

| 表示 | 几何形式 | 含义 |
| --- | --- | --- |
| 道路拓扑 | `nodes + edges` | 哪些路口相连 |
| 可行驶道路面 | 矩形与方形多边形集合 | 沥青实际占据的二维区域 |
| 车辆路线 | `route.points` 连续曲线 | 车辆在道路内计划跟随的路径 |

### 4.3 道路片如何组合

存储形式是“所有道路片组成的数组”，不是预先求并集后得到的单个复杂多边形。

对于城镇地图：

```text
每条 edge 生成 1 个道路矩形
每个 node 生成 1 个路口正方形
                  ↓
surfaces = [polygon₀, polygon₁, polygon₂, ...]
```

因此道路片数量通常为：

\[
|surfaces|=|edges|+|nodes|
\]

每个元素独立保存：

```js
{
  points: [{ x, z }, ...],
  minX,
  maxX,
  minZ,
  maxZ
}
```

路口面和道路面在连接位置发生重叠：

```text
                 道路矩形
                    │
                    │
             ┌──────┼──────┐
道路矩形 ────┼── 路口方形 ──┼──── 道路矩形
             └──────┼──────┘
                    │
                    │
                 道路矩形
```

数组中不会记录“这个道路片与哪个路口片相邻”，也不会把重叠边界消除。

不过从几何语义上，所有道路片共同表示一个可行驶区域：

\[
Road=Surface_0\cup Surface_1\cup\cdots\cup Surface_n
\]

也就是说：

```text
数据表示：多个独立多边形的数组
逻辑含义：这些多边形的并集
```

项目只在具体计算需要时实现并集效果。例如检查车辆道路占用时，会依次从车身多边形中减去每个道路片；全部处理后剩余的部分就是位于所有道路片并集之外的车身面积。计算道路横截面时，则分别求各道路片与横截线的区间，再把重叠或相接的区间合并。

这种方式避免了预先计算一个包含大量凹角和分支的全局复杂多边形，同时每个道路片的 `minX/maxX/minZ/maxZ` 可以用于快速排除不相关的面。

### 4.4 为什么变量名叫 `surfaces`

这里的 `surfaces` 不是三维建模中严格意义上的参数曲面或三角网格，而是“道路表面区域”的普通变量名。

每个元素实际是 `x-z` 平面上的二维多边形：

```js
{
  points: [{ x, z }, ...],
  minX,
  maxX,
  minZ,
  maxZ
}
```

它不包含三维曲面通常具有的信息：

- 没有 `y` 坐标；
- 没有法向量；
- 没有三角形索引；
- 没有曲面参数或高度变化。

这里使用 `surface`，是把每个多边形理解为一块俯视的“沥青道路表面”：

```text
三维世界中的道路
        ↓ 投影到地面
x-z 平面上的二维可行驶区域
        ↓
代码中称为 surface
```

所以更严格的变量名也可以是：

```text
roadPolygons
drivableAreas
asphaltPatches
```

`roadGeometry()` 返回的 `surfaces` 只表示二维逻辑道路几何。

## 5. 静态设施与道路标线

### 5.1 `world.objects`：按类型组织的对象集合

`world.objects` 是一个普通 JavaScript 对象数组。它把道路之外的地图对象集中存放在一起，例如建筑、树木、交通标志和高速公路设施。

数组中的对象并不是同一种固定结构，而是通过 `type` 区分的多种对象：

```text
world.objects
    ├── parcel
    ├── building
    ├── tree / bench
    ├── stop_sign / traffic_light
    ├── streetlight
    ├── town_sign / highway_sign / interstate_guide
    └── hill / overpass
```

所有对象通常都有以下公共字段：

| 字段 | 含义 |
|---|---|
| `id` | 对象标识，例如 `building-12` |
| `type` | 对象类型，决定还应读取哪些字段 |
| `x, z` | 对象在世界坐标系中的基准位置 |

不同类型再附加自己的字段：

| 类型 | 主要字段 | 静态含义 |
|---|---|---|
| `parcel` | `width, depth, park` | 一块城镇地块；`park` 表示是否作为公园地块 |
| `building` | `width, depth, height, rotation, style, color, roof` | 建筑的位置、占地尺寸、高度和朝向等属性 |
| `tree` | `height, kind` | 树的位置、树高和种类 |
| `bench` | `rotation` | 长椅的位置和朝向 |
| `stop_sign` | `nodeId, approach, height` | 某一路口驶入方向上的停车标志 |
| `traffic_light` | `nodeId, approach, height` | 某一路口驶入方向上的交通灯 |
| `streetlight` | `height` | 路灯的位置和高度 |
| `town_sign` | `text, height` | 城镇文字标志 |
| `highway_sign` | `width, height, text, direction, detail` | 高速公路标志及其文字信息 |
| `interstate_guide` | `approach, direction, text, detail` | 城镇驶向高速入口时的引导标志 |
| `hill` | `width, depth, height` | 山丘所占的区域及高度 |
| `overpass` | `width, depth, height` | 跨线结构的位置和尺寸 |

这里要注意两点。

第一，`x, z` 是对象的基准位置，但其具体语义由 `type` 决定。例如建筑的基准位置是矩形占地的中心，而交通标志只是一个点状设施的位置。

第二，并非所有对象都用矩形表示。建筑、地块、山丘和跨线结构具有 `width/depth`，可以解释为一个有方向或无方向的占地区域；树木、路灯和标志主要以位置点和高度描述。`world.objects` 本身也没有统一的 OBB 字段，使用者必须先查看 `type`。

因此，`world.objects` 更准确地说是一个按 `type` 区分结构的异构对象集合，而不是“所有元素共享同一个空间模型”的对象表。

### 5.2 交通设施如何与路口节点关联

路口的交通管制规则首先记录在道路图节点上：

```text
node.control = "stop"    停车标志路口
node.control = "signal"  信号灯路口
node.control = null       无交通管制
```

节点只说明“这个路口采用何种管制”。为了表示各个驶入方向上交通设施的实际位置，地图生成器还会在 `world.objects` 中创建 `stop_sign` 或 `traffic_light` 对象。

对路口的每一个相邻节点，代码都把它看作一个驶入方向，并创建一个设施对象：

```text
相邻节点 other ─────驶向────→ 路口 node
                         ↑
                 approach 表示该驶入航向

设施位置：位于路口前约 9 m，并向该行驶方向的右侧偏移 6.9 m
```

设施对象中的关键字段为：

| 字段 | 含义 |
|---|---|
| `nodeId` | 被该设施控制的路口节点 ID |
| `approach` | 从相邻节点驶向该路口时的航向 |
| `x, z` | 该方向上设施的实际世界位置 |
| `height` | 设施高度；停车标志为 2.8 m，交通灯为 4.8 m |

例如一个四岔路口有四条相邻道路，生成器会创建四个同类设施对象，而不是只在路口中心创建一个对象：

```text
             signal
                ↓
signal  →   [路口节点]   ←  signal
                ↑
             signal
```

所以二者的职责不同：

```text
node.control       = 路口层面的管制类型
object.nodeId      = 设施属于哪个路口
object.approach    = 设施控制哪个驶入方向
object.x / object.z = 设施放在哪里
```

交通灯当前显示什么颜色属于动态状态，不是这里讨论的静态地图对象字段。

### 5.3 交通设施与道路面的空间关系

严格来说，两者都不是。`stop_sign` 和 `traffic_light` 是 `world.objects` 中独立的点状设施对象，不属于节点正方形或 edge 道路长方形的组成部分。

其位置是以路口节点中心为基准计算的。若车辆沿航向 `h` 驶向路口，则设施的局部坐标相当于：

```text
ahead = -9 m     位于路口中心之前 9 m
right = +6.9 m   位于驶入方向右侧 6.9 m
```

城镇道路宽度为 12 m，因此道路边缘距离中心线为：

\[
\frac{12}{2}=6\text{ m}
\]

设施向右偏移 6.9 m，比道路边缘还多 0.9 m，所以其基准点通常落在驶入道路的右侧路边，而不是道路长方形内部。

路口正方形以节点为中心，向各方向延伸约 6.05 m。设施沿驶入方向后退了 9 m，也已经离开路口正方形。因此可将空间关系理解为：

```text
                  路口正方形
                ┌────────────┐
车辆行驶方向 →  │            │
================│     node   │================ 道路
            ●   └────────────┘
          交通设施
          位于驶入道路右侧路边

================ 表示宽 12 m 的道路区域
● 距道路中心线 6.9 m，超出道路边缘约 0.9 m
```

所以可以从三个层次区分：

| 内容 | 几何表示 |
|---|---|
| 路口 | `surfaces` 中以节点为中心的正方形 |
| 驶入道路 | `surfaces` 中连接两个节点的长方形 |
| 停车标志或交通灯 | `world.objects` 中独立的位置点，通过 `nodeId` 和 `approach` 与路口建立语义关联 |

这里的 `nodeId` 是引用关系，不表示设施在几何上被包含在 node 中。换言之，它在数据上独立，在语义上属于该路口的某个驶入方向，在空间上位于该方向的道路右侧。

### 5.4 参与驾驶逻辑的静态对象

如果只关注自动驾驶、交通违规和碰撞，`world.objects` 中需要保留关注的只有三类：

| 对象类型 | 自动驾驶 | 违规判定 | 碰撞判定 |
|---|---|---|---|
| `building` | 是：作为静态障碍物，并遮挡视线 | 否 | 是 |
| `stop_sign` | 是：让自动驾驶感知到停车管制设施 | 间接相关 | 否 |
| `traffic_light` | 是：让自动驾驶感知到信号灯及灯色 | 间接相关 | 否 |
| 其他静态对象 | 不进入核心决策 | 否 | 否 |

#### `building`

建筑是静态对象中唯一直接作为实体障碍物处理的类型，其矩形占地参与以下逻辑：

- 自动驾驶候选轨迹会检查是否可能撞上建筑；
- 车辆偏离道路后的恢复路径会绕开建筑；
- 重新规划驶回路线时，建筑会影响候选接入路径的评分；
- 建筑会遮挡车辆对交通参与者和交通设施的视线；
- ego 车辆与建筑矩形重叠时，会被记录为碰撞并终止驾驶。

因此，建筑的 `x, z, width, depth, rotation` 都具有实际逻辑意义，不只是外观参数。`height/style/color/roof` 则不参与当前二维驾驶与碰撞计算。

#### `stop_sign` 和 `traffic_light`

这两个对象会进入场景扫描。自动驾驶只有在感知范围、视场角和建筑遮挡条件允许时，才会把对应路口设施标记为可见；交通灯对象还会附带当前灯色。因此，它们影响自动驾驶收到的路口信息：

```text
设施对象可见
      ↓
根据 object.nodeId 找到路口
      ↓
自动驾驶收到 control、signal、stop_line 等信息
```

但是，实际交通规则和违规判定并不通过检测车辆是否碰到或越过标志对象完成。核心依据是：

```text
node.control                 路口是 stop 还是 signal
route.crossings[].stopS      车辆应停车和接受检查的位置
signalState(node, time, ...) 当前信号灯状态
```

当车辆的路线进度从 `stopS` 之前变为 `stopS` 之后时，模拟器检查：

- 停车标志路口是否已经完成停车；
- 信号灯路口是否在红灯状态下越线。

若不满足规则，才增加违规次数。因此 `stop_sign/traffic_light` 对违规判定是**间接相关**：它们负责可见设施和感知语义，真正的越线判定由路口节点和路线停车线完成。

这两个设施没有 `width/depth` 碰撞体，也没有被加入碰撞障碍物集合。车辆即使经过其位置，也不会产生碰撞事件。

### 5.5 停车线和斑马线

停车线和斑马线都不是 `world.objects` 中的独立对象，也没有 `stop_line` 或 `crosswalk` 类型。它们的表示方式并不完全相同。

#### 停车线：逻辑位置与可视标线

停车线具有一份用于驾驶规则的逻辑位置：`route.crossings[].stopS`。它不是直接保存的 `(x,z)`，但可以通过路线恢复世界坐标：

```js
const p = pointAt(route.points, crossing.stopS);
// p.x、p.z 是逻辑停车线在当前车道中心的位置
// crossing.approach 给出停车线对应的驶入航向
```

因此，从逻辑模型看，停车线有可计算的世界坐标，但它附属于 route 的 crossing，而不是地图 object。

场景中的白色停车标线则由场景构建代码直接根据路口 node 和相邻道路方向生成。每个路口入口都会绘制一条垂直于车道方向、宽约 5 m 的窄矩形标线，其中心位于 node 前约 10 m，并横向位于驶入车道中心。

逻辑停车线按 node 前 10.5 m 计算，可视标线按约 10 m 绘制，两者位于同一区域但存在约 0.5 m 的偏移；它们不是同一个共享的对象实例。

```text
world.objects                 没有停车线对象
route.crossings[].stopS       规则判断使用的逻辑位置
scene 根据 node 直接构造矩形  可视停车标线
```

#### 斑马线：由 node 直接生成的标线

斑马线没有类似 `stopS` 的地图逻辑字段，也没有独立保存的 `(x,z)` 对象。场景构建时遍历每个路口 node 及其相邻道路，在距 node 中心约 7 m 的位置生成一组白色小矩形条纹：

```text
驶入方向 →

──── 停车线 ─── 斑马线 ── 路口正方形
      约 10 m      约 7 m       边界约 6.05 m
```

这些条纹在构造时当然会得到实际世界坐标，但坐标是从 `node.x/node.z` 和相邻节点方向即时计算出来的，没有作为地图数据保存，也不会进入碰撞或道路规则判断。

行人过街逻辑也不是通过查询“斑马线对象”实现的。过街行人是独立的动态实体，以 `nodeId` 关联路口，并使用自己计算出的过街路径；可视斑马线只是在相近位置提供道路标记。

所以二者可以概括为：

| 内容 | 是否是 `world.objects` | 是否有逻辑位置 | 生成方式 |
|---|---:|---|---|
| 停车线 | 否 | 有，`crossing.stopS` 可恢复 `(x,z)` | 逻辑位置随 route 生成；可视标线按 node 另行生成 |
| 斑马线 | 否 | 没有独立地图字段 | 按 node 和道路方向直接生成条纹 |

### 5.6 可暂时忽略的装饰或环境对象

以下类型当前不参与核心自动驾驶决策、违规判定或碰撞判定：

```text
parcel
tree
bench
streetlight
town_sign
highway_sign
interstate_guide
hill
overpass
```

其中部分对象会出现在完整世界信息或通用观测数据中，但自动驾驶使用的精简场景扫描不会把它们作为决策对象，碰撞系统也不会把它们作为障碍物。因此，在后续分析驾驶模型时可以先忽略。

需要注意，动态的汽车、摩托车和行人虽然不属于 `world.objects` 静态对象数组，却都与自动驾驶和碰撞直接相关；行人和其他车辆也会参与冲突、让行等判断。它们应放到模拟器动态实体模型中单独讨论。

## 6. 任务路线

### 6.1 `route`：从道路图路径到连续行驶路线

道路图的 `nodes + edges` 描述“哪些节点之间可以通行”，而 `route` 描述车辆具体沿哪条连续路径行驶。它是在道路图上选出一串节点后生成的车道级路线。

可以把它理解为本次驾驶任务的**当前规划路线或导航线路**：从任务起点出发，在完整道路网中选择一条通往任务终点的路径。它不是地图中所有可能道路的集合，而是其中被选中的一条。

```text
完整地图 road graph
├── 许多可选道路
├── 许多可选路口
└── 本次选择的一条路径 ──→ world.route
```

这里的“从起点到终点”是任务语义。几何上，城镇路线的第一个 `points` 点会放在起始节点之后约 14 m，最后一个点会放在目的节点之前约 15 m，而不是要求轨迹点恰好位于两个节点中心。

### 6.2 `route` 的生成时机

初始 `route` 是地图生成流程的最后一步，与 `world` 一起返回：

```text
生成 nodes、edges 和 objects
             ↓
确定 startNode、nextNode、destination
             ↓
在道路图中选择节点路径
             ↓
makeRoute(...) / makeHighwayRoute(...)
             ↓
写入 world.route
             ↓
返回完整 world
```

城镇和城市地图会先随机选择远端的 `destination`，再用最短路径算法计算从起步方向通往该终点的节点序列；其随机选择由地图 `seed` 控制。高速地图则直接使用一组预先规定的节点顺序，依次经过起点城镇、入口匝道、高速主路、出口匝道和终点城镇。

因此更准确地说，`route` 不是与 `nodes/edges` 同时产生的基础路网，而是**路网生成完成之后，根据本次任务起终点派生出来的初始导航路线**。

模拟开始时：

```text
player.route = world.route
```

ego 的初始位置和航向也取自这条路线的前两个几何点。如果驾驶过程中车辆明显偏离路线，模拟器可以从当前位置重新规划到原目的地，并同时替换 `player.route` 和 `world.route`。所以 `world.route` 表示当前路线，不保证整个驾驶过程中永远保持初始值。

```text
道路图中的节点序列
        ids
         ↓
生成连续车道中心轨迹
       points
         ↓
附加路口信息和分段属性
 crossings / sections
```

一个路线对象的主要字段是：

| 字段 | 数据形式 | 含义 |
|---|---|---|
| `ids` | 节点 ID 数组 | 路线经过的拓扑节点顺序 |
| `points` | `{x,z,s}` 数组 | 车辆实际跟随的连续折线采样点 |
| `crossings` | 路口记录数组 | 路线如何进入、通过并离开各路口 |
| `sections` | 路段记录数组 | 高速路线不同区段的静态属性；城镇路线没有该字段 |
| `length` | 数值 | 路线总长度，即最后一个点的累计里程 `s` |

### 6.3 `ids`：拓扑层路径

`ids` 只表达节点顺序，例如：

```text
["n0", "n1", "n5", "n9"]
```

其中每个元素都只是 `node.id`，不包含 `edge.id`。例如上述序列表达：

```text
node n0 ── edge(n0,n1) ── node n1 ── edge(n1,n5) ── node n5 ── edge(n5,n9) ── node n9

route.ids 实际保存： [n0, n1, n5, n9]
                       不保存中间的 edge ID
```

所经过的 edge 由相邻两个节点 ID 间接确定。生成路线时，代码依次取：

```text
(ids[0], ids[1])
(ids[1], ids[2])
(ids[2], ids[3])
```

再在 `world.edges` 中查找连接这两个节点的 edge。对于单向 edge，还必须保证节点顺序与 `edge.a → edge.b` 的方向一致；双向 edge 则允许反向匹配。

因此，`ids` 可以说明路线依次经过哪些节点，并可据此推导经过哪些道路，但它本身不能直接告诉车辆每一米应位于哪里，因为节点一般位于道路或路口的中心。连续位置由 `route.points` 表示。

### 6.4 `points`：几何层路径

`points` 把节点路径转换为靠右行驶的车道中心轨迹。每个点包含：

```js
{ x, z, s }
```

- `x, z` 是世界坐标；
- `s` 是从路线起点沿折线累计得到的里程；
- 相邻点通常经过约 1 m 间隔的重采样。

城镇道路中，直线路段沿车道中心生成；转弯处使用曲线连接驶入车道和驶出车道；掉头则使用半圆形轨迹。因此 `points` 是真正可供定位和跟踪的连续路线，而不只是节点连线。

它的核心作用是把离散的拓扑导航转换成可以按距离查询的连续几何参考线：

```text
ids：     node A ───── node B ───── node C
                     只说明经过哪些节点

points：  · · · · · · · · · ╮
                              ╰ · · · · ·
                     表示车道中心和转弯曲线
```

具体有以下用途：

1. **确定路线上的连续位置。** `pointAt(points, s)` 可以查询沿路线前进到里程 `s` 时的 `(x,z)`，并根据所在折线段得到航向。查询结果可以位于两个采样点之间，并不是只能返回数组中的原始点。
2. **确定车辆的路线进度。** `nearestOnPath(vehicle, points)` 把车辆当前位置投影到最近的路线折线段，得到最近点、距离、路线航向和累计里程 `s`。因此系统能知道车辆走到哪里、偏离路线多远。
3. **描述车道和转弯形状。** `ids` 连接的是路口中心，不能表示靠右车道、转弯圆弧或匝道曲线；`points` 保存这些实际行驶几何。
4. **统一引用沿线位置。** 路口停车位置使用 `crossing.stopS`，终点使用 `points` 的最后一个点，向前观察也可以查询 `s + d` 处的位置。
5. **提供路线跟踪参考。** 车辆可以查询当前位置前方一定距离的路线点，据此计算应该朝哪个方向行驶。

例如：

```text
points = [
  {x: 10, z: 20, s: 0},
  {x: 10, z: 19, s: 1},
  {x: 10, z: 18, s: 2}
]
```

其中 `s=1.5` 表示沿路线走了 1.5 m。通过相邻点插值，可得到大约 `(x=10,z=18.5)`，即使数组中没有直接保存这个点。

所以 `points` 不是另一组拓扑节点，也不是要求车辆逐点跳转的离散位置；它是一条由密集采样点表示、可插值的路线参考折线。

#### 转弯路线如何生成

城镇路线经过一个中间路口节点 `p` 时，生成器先计算两个方向：

```text
hin   = 上一个节点 → 当前路口 p 的驶入航向
hout  = 当前路口 p → 下一个节点的驶出航向
```

然后在道路中心线右侧 3 m 处取得右侧车道中心，并确定：

```text
a = 驶入车道上、路口中心前 11 m 的进入点
b = 驶出车道上、路口中心后 11 m 的离开点
```

`a`、`b` 不是车道中心线与路口正方形边界的交点。代码没有对车道线和路口多边形执行求交，而是直接以 node 中心为基准，沿驶入和驶出方向各取 11 m。

城镇路口正方形从 node 中心向四周只延伸约 6.05 m。若把驶入和驶出方向分别展开成一维距离示意，则有：

```text
驶入方向 →

──── a ─────── 路口边界 ┌───────────┐ 路口边界 ─────── b ────→
     -11 m       -6.05 m │  node 0 m │  +6.05 m        +11 m
                         └───────────┘
```

所以 `a` 位于驶入道路长方形内部、但在路口正方形之前约：

\[
11-6.05=4.95\text{ m}
\]

`b` 同理，位于驶出道路长方形内部、路口正方形之后约 4.95 m。二者横向都位于道路中心线右侧 3 m，即对应方向的右侧车道中心。

这样设计意味着转弯曲线不是进入路口正方形后才突然开始，而是在到达路口边界之前就开始弯曲，并在离开路口边界后再结束，从而得到更平滑的路线。

```text
驶入车道                         驶出车道
──────────── a                 b ───────────→
               ╲             ╱
                ╲  转弯曲线  ╱
                 [路口中心 p]
```

之后根据 `hin` 和 `hout` 的夹角分三种情况。

##### 普通左转或右转

普通 90° 转弯使用二次 Bézier 曲线连接 `a` 和 `b`。控制点 `c` 取两条右侧车道中心线的交点：

```text
a ───────── c
             ╲
              ╲
               b
```

曲线公式为：

\[
P(t)=(1-t)^2a+2(1-t)t c+t^2b,\qquad 0\leq t\leq1
\]

代码把 `t` 均分为 16 段，计算曲线上的点。`a` 决定曲线从哪里进入路口，`b` 决定从哪里离开，`c` 把两端的行驶方向平滑连接起来。车辆路线因此不会从驶入直线突然折成 90°。

在当前横平竖直的城镇路网中，控制点可以通过组合 `a`、`b` 的横纵坐标得到：

```text
c = (b.x, a.z)  或  (a.x, b.z)
```

选择哪一种取决于驶入道路是横向还是纵向。本质上，它是在求驶入车道延长线与驶出车道延长线的交点。

##### 直行

如果 `hin` 和 `hout` 基本相同，就不需要转弯曲线，直接从 `a` 连接到 `b`。

##### 掉头

如果两者方向几乎相反，则使用半径为 3 m 的半圆，并采样 24 段，把当前方向的右侧车道连续连接到反方向车道。

完成各个路口的连接后，所有直线点和转弯点会组成一条 `raw` 折线，再由 `samplePolyline(raw)` 按约 1 m 间隔重新采样，最终形成 `route.points`：

```text
节点方向
   ↓
进入点 a + 离开点 b
   ↓
直线 / 二次 Bézier / 半圆
   ↓
拼接为 raw 路线
   ↓
约 1 m 间隔重新采样
   ↓
route.points
```

##### 高速地图中的转弯

高速路线的处理略有不同：

- 高速主路直接沿 `roadSamples` 的曲线生成车道轨迹；
- `onramp`、`offramp` 等连接道路本身已经保存了三次 Bézier 曲线路径，route 直接使用这些 `edge.path`；
- 高速地图两端城镇中的路口转弯，再使用三次 Bézier 曲线平滑连接驶入和驶出车道。右转通常在路口前后各截取约 11 m，左转约 14 m，再用两个控制点保持进入和离开方向。

这些曲线都只是静态的路线参考几何，并不是车辆真实运动轨迹。车辆是否严格沿曲线行驶，还取决于后续的转向控制和运动学更新。

#### 城镇路线是固定模板的组合

由于城镇和城市路网具有以下固定条件：

- 道路都是水平或竖直的正交道路；
- 道路宽度固定为 12 m；
- 路口正方形边长固定为约 12.1 m；
- 右侧车道中心固定偏离道路中心线 3 m；
- 转弯进入点和离开点固定距 node 中心 11 m；

所以路线的局部几何确实由少数固定模式组成：

| 模式 | 生成方式 | 固定参数 |
|---|---|---|
| 直线路段 | 沿右侧车道中心连接 | 横向偏移 3 m |
| 路口直行 | 直接连接进入点 `a` 和离开点 `b` | 路口前后各 11 m |
| 左转或右转 | 二次 Bézier 曲线 | `a、b、c` 和 16 段曲线采样 |
| 掉头 | 半圆曲线 | 半径 3 m、24 段采样 |

可以把整条城镇路线理解为这些几何积木的拼接：

```text
直线 ── 右转 ── 直线 ── 路口直行 ── 直线 ── 左转 ── 直线

或

直线 ── 掉头 ── 直线
```

固定的是**局部形状模板及其尺寸参数**，不固定的是：

- 相邻路口之间的距离，因此直线路段长度会变化；
- 哪些纵向道路存在，因此可选择的拓扑路径会变化；
- 起点、目的地和最短路径，因此左转、右转、直行的排列顺序会变化；
- 采样后的具体点数，长路段会产生更多 `points`。

因此，城镇路线不是每张地图都具有完全相同的整体形状，而是：

> 使用固定的直线、路口转弯和掉头模板，根据随机生成的道路图和本次导航路径进行不同组合。

这个结论主要适用于 `town/city`。高速地图还包含正弦变化的主路中心线和三次 Bézier 匝道，因此高速路线的曲率和整体形状不只由上述三种城镇模板构成。

### 6.5 `crossings` 和 `sections` 的生成时机

这两个数组都在 `route` 生成时一次性构造，不是车辆实际经过路口或路段之后才追加的驾驶记录。

```text
生成 route
   ├── 生成 ids
   ├── 生成 points
   ├── 预先生成 crossings
   └── 预先生成 sections（仅高速）

开始驾驶
   └── 读取这些数组，判断当前位于哪里、前方有什么
```

`crossings` 会在生成路线几何时，遍历路线中的中间路口并提前写入。等 `points` 完成后，再计算每个路口停车位置对应的 `stopS`。因此即使 ego 尚未出发，路线将经过的所有路口记录已经存在。

`sections` 在生成高速路线时，随着每条 edge 的几何加入路线而同步创建。它预先记录各段路线的 `kind、name、startS、endS、speedLimit、laneHalfWidth`；相邻且类型、限速相同的区段会被合并。城镇和城市路线不生成 `sections`。

实际驾驶时，模拟器不会因为“刚经过一个路口”就在 `crossings` 中添加元素，也不会因为“驶入高速”就在 `sections` 中添加元素。它主要用车辆当前的路线里程 `player.s` 去查询这些预先存在的区间和位置：

```text
player.s 接近 crossing.stopS
    → 前方到达路口停车线

section.startS <= player.s <= section.endS
    → 当前位于这个高速路段
```

真正的运行时状态另行保存。例如车辆是否已经在某停车标志前完成停车，记录在车辆的 `stops` 或路口记忆中，而不写回 `crossings`。如果车辆偏离路线并触发重新规划，则会生成一个新的 route，新 route 也会带有重新计算的 `crossings` 和 `sections`。

### 6.6 `crossings`：通过路口的方式

每经过一个中间路口，路线会记录：

```js
{
  nodeId,
  x,
  z,
  approach,
  exit,
  stopS
}
```

| 字段 | 含义 |
|---|---|
| `nodeId` | 路口节点 ID |
| `x, z` | 路口节点的世界位置 |
| `approach` | 进入路口时的航向 |
| `exit` | 离开路口时的航向 |
| `stopS` | 路线上的停车位置，用累计里程表示 |

对于标准 `town/city` 路网，道路都是横平竖直的，因此 `approach` 和 `exit` 通常就是四个基本方向：

| 航向值 | 世界方向 |
|---:|---|
| `0` | 北，即 `-z` |
| `π/2` | 东，即 `+x` |
| `π` 或 `-π` | 南，即 `+z` |
| `-π/2` | 西，即 `-x` |

例如：

```text
approach = 0
exit     = π/2
```

表示车辆从南向北进入路口，然后向东驶出，即右转。不过 `approach/exit` 的数据类型仍是普通弧度角，而不是只能取“上、下、左、右”的枚举；高速地图中的曲线连接可以产生非严格四方向的航向。

`stopS` 不是另一个世界坐标，而是 `points` 上的一个一维位置。例如 `stopS = 84` 表示停车线位于从路线起点出发约 84 m 的位置。通过路线插值即可将它恢复为对应的 `(x,z)`。

它在语义上确实表示**驶入路口前的停车线位置**。城镇路线先在驶入方向的右侧车道中心上取一个目标点：

```text
横向：道路中心线右侧 3 m
纵向：路口 node 中心之前 10.5 m
```

然后在 `route.points` 中寻找离这个目标最近的位置，并把该点的累计里程保存为 `stopS`。

```text
驶入方向 →

───────── 停车线 ───────── 路口边界 ┌───────────┐
          -10.5 m             -6.05 m │  node 0 m │
                                      └───────────┘
```

因此停车线位于路口正方形之前约 `10.5-6.05=4.45 m`。车辆越过 `stopS`，就表示其路线进度已经通过这条驶入停车线；红灯和停车标志违规正是以是否越过这个位置为基础判断。

需要注意，数据中没有保存一条横跨车道的线段多边形。`stopS` 只保存路线上的纵向位置；使用时通过 `pointAt(route.points, stopS)` 得到停车线中心位置，再结合 `approach` 把它理解为一条垂直于行驶方向的停车线。

### 6.7 `sections`：高速路线的属性分段

高速路线还会将不同性质的路段记录为：

```js
{
  kind,
  name,
  startS,
  endS,
  speedLimit,
  laneHalfWidth
}
```

其中 `startS/endS` 是该区段在路线累计里程上的范围，`kind` 区分城镇道路、高速主路和连接道路等类型，`speedLimit` 是限速，`laneHalfWidth` 是当前路线所用车道的半宽。相邻且类型、限速相同的区段可以合并成一个较长的 section。

因此，`route` 不能等同于道路本身：

```text
world.edges / surfaces = 地图允许在哪里通行
route                   = 本次任务选择沿哪里行驶
```

## 7. 静态地图模型总结

地图系统的静态表示可以概括为四层：

```text
world 元数据与边界
        ↓
nodes + edges 道路拓扑
        ↓
surfaces 道路二维占用区域
        ↓
objects / route / 高速注记
地图对象、任务路线和附加语义
```
